# Nexus 仓库治理总纲

> 文档状态: Active
> 文档角色: 当前阶段仓库治理总纲
> 适用范围: 仓库根目录、`nexus-platform`、`nexus-core`、`nexus-contracts`、`docs/`、构建与发布流程
> 最后更新: 2026-04-20

## 1. 文档定位

本文档用于定义当前仓库从个人兴趣项目向正式公司项目治理转换时的统一范围、边界、优先级和执行原则。

它不是某一个专题方案，也不是一次性重构说明，而是后续所有整理动作的总纲。

在治理阶段，若本文件与其他开发文档存在冲突，应以本文件为准；其他文档应作为专题补充文档，后续再逐步对齐。

当前应视为本总纲下的专题文档包括：

1. `05-Versioning_Strategy.md`
2. `07-Cross_Platform_Refactor_Plan.md`
3. `08-Cross_Platform_Build_and_Dependencies.md`
4. `09-Contracts_and_Repo_Organization_Proposal.md`
5. `10-Variant_Build_and_Artifact_Engineering.md`

## 2. 当前状态判断

当前仓库已经具备明确的 monorepo 雏形，但整体仍处于半迁移态。

所谓半迁移态，指的是：

1. 新结构已经出现，但旧结构残留仍然大量存在。
2. 真实代码边界已经变化，但文档和脚本没有同步完成收口。
3. 新构建入口已经存在，但旧入口仍在继续承担事实入口角色。
4. 专题方案已经不少，但缺少一个当前有效的总治理基线。

因此，本轮治理的重点不是继续堆叠设计文档，而是先明确当前事实、明确权威边界、明确优先级，再逐步清理历史残留。

## 3. 治理范围

本轮治理纳入范围的内容包括：

### 3.1 文件与目录组织

目标是让目录语义、职责分层和真实代码位置一致，减少重复表达和历史堆叠。

### 3.2 版本管理

目标是建立可解释、可维护、可发布的版本治理规则，避免多个版本源长期漂移。

### 3.3 文档管理

目标是建立文档权威关系、状态标记和更新规则，防止文档继续失真。

### 3.4 CI / CD 与质量门禁

目标是让代码、构建、测试和发布不再只依赖本地经验和手动操作。

### 3.5 多平台兼容治理

目标是建立真实的多平台能力边界、兼容策略和构建矩阵，而不是继续维持“文档兼容、实际未验证”的状态。

## 4. 不在本轮直接解决的内容

为避免治理范围失控，本轮不直接追求以下结果：

1. 不在当前阶段重写全部前端交互或视觉体系。
2. 不要求所有历史工具立即完成统一重构。
3. 不要求一次性完成所有平台的正式发布链路。
4. 不要求先把全部旧文档全部重写完再开始代码治理。
5. 不为了“看起来更整齐”而进行大规模无收益目录搬移。

## 5. 治理原则

### 5.1 先统一事实源，再做结构优化

先定义哪些入口、哪些目录、哪些文档、哪些版本字段是当前权威，再做后续重构。

### 5.2 先收边界，再补能力

正式项目治理首先关注职责清晰、依赖明确和可验证性，而不是继续扩展功能面。

### 5.3 先建立稳定执行路径，再清理历史残留

旧脚本、旧路径、旧文档可以暂时保留，但必须明确其地位，不能继续和现行路径并列为事实入口。

### 5.4 文档必须服务真实仓库

文档不是愿景板。凡是写入开发文档的路径、入口、流程和约束，都必须能在仓库现状中落到具体目录或具体文件。

### 5.5 治理以可验证为前提

任何治理结论都应尽量转化为可检查的文件结构、命名规则、构建命令、测试门禁或 CI 规则。

## 6. 当前权威边界

### 6.1 仓库分层边界

当前仓库应按以下三层理解：

1. `nexus-contracts`: 共享契约层
2. `nexus-core`: 逻辑实现层
3. `nexus-platform`: 桌面宿主层

当前阶段不再把仓库理解为单一桌面应用目录。

### 6.2 目录职责边界

仓库根目录下的主要目录应按以下语义解释：

1. `docs/`: 正式文档与工程规范
2. `build-system/`: 统一构建入口与构建逻辑
3. `profiles/`: 构建与能力档位 profile
4. `scripts/`: 仓库级包装脚本与兼容入口
5. `tools/`: 外部工具与二进制资源
6. `artifacts/`: 构建产物目录

若后续出现职责重叠，应优先收敛到上述解释，而不是再引入新的并行入口。

### 6.3 依赖方向边界

当前和后续都应遵循以下依赖方向：

1. `nexus-platform` 可以依赖 `nexus-core`
2. `nexus-platform` 可以依赖 `nexus-contracts`
3. `nexus-core` 可以依赖 `nexus-contracts`
4. `nexus-contracts` 不应依赖 `nexus-core` 或 `nexus-platform`

### 6.4 文档权威边界

当前治理阶段的文档优先级应为：

1. 本文档定义治理总范围与总边界
2. `docs/README.md` 负责文档索引
3. 专题文档负责单项方案细化
4. `.local.md` 文件仅作为本地工作笔记，不作为正式规范

## 7. 文件与目录组织基线

### 7.1 根目录组织基线

根目录只应承载以下类型的内容：

1. monorepo 子项目
2. 文档中心
3. 构建系统
4. profile 与脚本
5. 外部工具与产物
6. 仓库级配置

不应继续把新的业务代码、临时脚本和说明文件随意散落到根目录。

### 7.2 `nexus-platform` 组织基线

`nexus-platform` 作为桌面宿主层，后续应逐步收敛为：

1. `backend/`: 宿主 API、manager、平台适配、运行支持代码
2. `frontend/`: React 应用与设计系统资源
3. `config/`: 宿主运行配置与版本信息
4. `tests/`: 宿主层测试
5. `run.py`: GUI 启动入口

当前阶段允许历史结构存在，但后续新增内容必须尽量向上述语义收敛。

### 7.3 `backend/` 组织基线

`nexus-platform/backend/` 后续应明确区分四类职责：

1. 应用壳与 API 暴露
2. manager 层与桥接调度
3. 平台能力与平台特化实现
4. 分析或工具支持模块

禁止继续把宿主入口、平台特化、业务逻辑和运行时数据路径长期混杂在同一层次中。

### 7.4 `frontend/` 组织基线

`nexus-platform/frontend/src/` 后续应逐步区分：

1. `components/`: 通用组件与可复用 UI
2. `features/` 或等价分层: 按工具域组织的页面逻辑
3. `hooks/`: 共享 Hook
4. `lib/` / `utils/`: 非 UI 的前端支撑逻辑
5. `translations.js`: 多语言入口

当前 `components/` 中工具面板、调试页面、基础组件和设计系统组件并列存在，后续应作为重点整理面。

### 7.5 脚本组织基线

脚本层必须区分三类角色：

1. `build-system/`: 真实构建逻辑
2. `scripts/`: 仓库级兼容包装或开发入口
3. `nexus-platform/scripts/`: 子项目局部脚本，仅在仍有实际必要时保留

后续原则是让 `build-system` 成为真实执行入口，其他脚本尽量退化为薄包装。

## 8. 版本管理基线

### 8.1 版本治理目标

版本管理需要回答四个问题：

1. 对外发布版本看哪里
2. 各子项目包版本看哪里
3. 哪个字段是当前单一事实源
4. 发布时哪些版本必须同步更新

### 8.2 当前临时基线

在统一版本系统落地前，当前阶段采用以下临时规则：

1. 面向整体产品的应用版本以 `nexus-platform/config/versions.json` 中的 `app` 为准
2. `nexus-core` 与 `nexus-contracts` 的包版本继续保留在各自打包元数据中
3. 不允许再新增第四套平行版本源
4. 所有文档必须明确写出引用的是“产品版本”还是“包版本”

### 8.3 目标状态

后续应将版本治理收敛为：

1. 一个清晰的产品版本事实源
2. 可追踪的子包版本关系
3. 可由构建系统读取并注入的版本信息
4. 能在 CI 与产物 manifest 中自动体现的版本数据

## 9. 文档管理基线

### 9.1 文档分类

文档应按以下四类治理：

1. `Active`: 当前有效规范或指南
2. `Draft`: 正在设计中的方案
3. `Proposal`: 提案型文档，未成为正式规则
4. `Archive`: 历史文档，仅供回溯

后续 development 文档应显式标记状态，避免读者无法判断“这是现行规则还是历史思路”。

### 9.2 文档入口

当前正式文档入口应统一收敛到：

1. `README.md`: 仓库外层介绍
2. `docs/README.md`: 文档中心索引
3. 本文档: 开发治理总纲

### 9.3 文档更新规则

后续任何涉及以下内容的代码变更，都应同步检查对应文档是否失效：

1. 目录结构
2. 构建入口
3. 版本字段
4. 平台支持状态
5. CI / 发布流程

### 9.4 本地文档规则

仅供个人使用的 development 笔记统一使用 `*.local.md` 命名，并通过 `.gitignore` 排除，不进入正式规范体系。

## 10. CI / CD 基线

### 10.1 CI 的目标

CI 不是为了“看起来专业”，而是为了把当前高度依赖人工经验的仓库状态转成机器可验证状态。

### 10.2 最小 CI 分层

建议后续至少拆成两层：

1. `Validate`: 安装、导入、前端构建、基础测试、lint 或等价检查
2. `Package`: 按目标平台构建正式产物

### 10.3 最小门禁

正式接入前，至少需要建立以下门禁：

1. Python 依赖安装成功
2. 前端依赖安装与 `npm run build` 成功
3. 关键 Python 模块可导入
4. 最小测试集通过
5. 统一构建入口可执行

### 10.4 产物策略

产物应由目标平台原生构建，不把跨平台交叉打包作为正式主路径。

## 11. 多平台兼容基线

### 11.1 平台支持必须显式分级

后续所有文档与发布说明都必须明确区分：

1. 完全支持
2. 部分支持
3. 实验支持
4. 尚未支持

### 11.2 当前兼容治理方向

当前方向应为：

1. Windows 继续作为主成熟平台
2. macOS 以“稳定启动与核心通用能力可用”为第一阶段目标
3. Linux 以“可验证构建与最小运行能力”为后续阶段目标

### 11.3 能力优先于理想兼容

多平台兼容不要求所有功能完全一致，而要求系统能根据平台能力显式降级、显式隐藏、显式告警。

## 12. 执行阶段建议

### Phase 1: 统一事实源

目标：统一入口、路径、文档权威关系。

范围：

1. 更新 AI 指引
2. 更新开发指南与文档中心索引
3. 明确构建入口与脚本地位
4. 明确版本与平台支持的现阶段规则

### Phase 2: 收敛结构边界

目标：开始整理目录职责和模块边界。

范围：

1. `backend/` 结构收口
2. `frontend/src/` 分层收口
3. 脚本入口收口
4. 测试与工作区配置修正

### Phase 3: 建立工程门禁

目标：把治理要求落成自动检查。

范围：

1. 最小测试集
2. 最小 CI
3. 统一构建校验
4. 平台矩阵验证

### Phase 4: 发布体系收口

目标：形成正式项目级的版本、产物和发布闭环。

范围：

1. 版本事实源统一
2. 产物 manifest 统一
3. 多平台发布流程成型
4. 历史脚本和历史文档继续退役

## 13. 治理完成的判断标准

当以下条件大部分满足时，可视为本轮治理进入稳定阶段：

1. 新开发者能在不依赖口头说明的情况下找到真实入口与真实结构
2. 主要开发文档不再与仓库事实明显冲突
3. 构建与发布入口已经明确，旧脚本不再承担事实标准角色
4. 版本信息可以被稳定解释、稳定读取、稳定输出
5. CI 能够阻止明显失真或失配进入主线
6. 平台支持矩阵不再是口头共识，而是文档和流水线中的显式规则

## 14. 当前结论

当前仓库不是没有结构，而是缺少一个被所有后续整治动作共同承认的治理基线。

本文件的目标，就是把这条基线明确下来：

1. 后续整理不再以零散讨论为准
2. 后续专题文档不再各自争夺总解释权
3. 后续代码与文档治理都要围绕统一的范围和边界推进
