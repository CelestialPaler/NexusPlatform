# Nexus 文档治理与收口方案

> 文档状态: Active
> 文档角色: docs 体系治理基线 / 文档收口执行方案
> 适用范围: `docs/`、仓库根 `README.md`、各子项目 `README.md`、API / 架构 / development 文档
> 最后更新: 2026-04-21

## 1. 文档目的

本文档用于回答三个问题：

1. Nexus 的文档体系应该如何分层。
2. 哪些文档在当前阶段承担正式权威角色。
3. 当前 docs 需要按什么顺序收口，才能把项目从个人开发状态转为边界清晰、版本明确、路径可靠的正式软件工程项目。

本文档不是某一篇单独技术说明，而是 `docs/` 目录本身的治理规则。

若后续对文档组织、文档命名、文档状态、文档入口存在冲突，应优先以本文档与 `docs/development/11-Repository_Governance_Baseline.md` 为准。

## 2. 当前问题判断

当前 docs 的主要问题不是“文档数量少”，而是“多套叙事并存、权威边界不清、入口文档仍有历史口径”。

典型表现包括：

1. 文档中心已有新总文档，但索引页本身仍保留旧版本元信息和旧说明方式。
2. 部分总入口文档仍使用过时技术栈或历史目录叙事。
3. API、架构、开发文档之间没有统一的状态说明和权威关系。
4. 读者无法快速判断某篇文档是现行规则、专题草案还是历史残留。
5. `docs/` 虽然内容不少，但还没有形成“可持续指导开发”的正式文档体系。

因此，本轮收口的目标不是继续堆文档，而是把文档本身工程化。

## 3. 文档治理目标

Nexus 的 docs 后续应同时满足以下目标：

1. **定义清晰**: 能清楚说明项目定义、边界、版本、系统构成和工程约束。
2. **路径可靠**: 文档中出现的目录、入口、命令和事实源必须对应真实仓库。
3. **权威明确**: 每类问题都能找到单一优先参考文档。
4. **状态可辨**: 读者能立即判断文档是 Active、Draft、Proposal 还是 Archive。
5. **开发可用**: 文档要能直接指导研发、构建、发布、扩展和治理动作。
6. **可持续维护**: 文档更新规则必须能够跟随代码与结构变化持续演进。

## 4. 推荐的文档分层

Nexus 的文档体系建议稳定为五层，而不是继续平铺。

### 4.1 总说明层

用于定义项目是什么。

当前主文档：

1. `docs/00-设计概要.md`

职责：

1. 项目定义
2. 产品边界
3. 版本状态
4. 总体架构
5. 技术栈
6. 构建与交付方向
7. 规划与风险

### 4.2 用户说明层

用于定义产品怎么使用。

当前主文档：

1. `docs/02-使用指南.md`

职责：

1. 安装与启动
2. 功能使用说明
3. 故障排查
4. 面向测试、现场和终端用户的操作手册

### 4.3 开发入口层

用于定义研发如何进入项目。

当前主文档：

1. `docs/03-开发指南.md`

职责：

1. 给新开发者提供阅读顺序
2. 提供开发常用入口和最小命令
3. 指向各类正式专题规范

这一层应该是“研发入口页”，而不是把所有细节都堆在一篇文档里。

### 4.4 工程规范层

用于定义正式工程规则。

当前主文档应包括：

1. `docs/development/11-Repository_Governance_Baseline.md`
2. `docs/development/12-Documentation_Governance_and_Closure_Plan.md`
3. `docs/development/05-Versioning_Strategy.md`

专题补充文档包括：

1. `docs/development/07-Cross_Platform_Refactor_Plan.md`
2. `docs/development/08-Cross_Platform_Build_and_Dependencies.md`
3. `docs/development/09-Contracts_and_Repo_Organization_Proposal.md`
4. `docs/development/10-Variant_Build_and_Artifact_Engineering.md`

### 4.5 参考资料层

用于承载 API、架构说明和专题参考。

对应目录：

1. `docs/api/`
2. `docs/architecture/`

这一层可以保留更多细节，但必须明确状态，避免与总说明层或工程规范层争夺解释权。

## 5. 当前权威文档矩阵

为了避免“每类问题打开三篇文档还不知道该信谁”，当前阶段应明确以下权威关系。

### 5.1 项目定义与立项说明

优先文档：

1. `docs/00-设计概要.md`

### 5.2 仓库治理、边界与执行优先级

优先文档：

1. `docs/development/11-Repository_Governance_Baseline.md`

### 5.3 文档体系自身治理

优先文档：

1. `docs/development/12-Documentation_Governance_and_Closure_Plan.md`

### 5.4 版本事实源与版本规则

优先文档：

1. `docs/development/05-Versioning_Strategy.md`

### 5.5 开发阅读入口

优先文档：

1. `docs/03-开发指南.md`

### 5.6 API 与架构参考

优先目录：

1. `docs/api/`
2. `docs/architecture/`

但这两类文档默认属于“参考层”，除非显式声明为 Active，否则不自动承担工程总规则角色。

## 6. 文档状态与强制元信息

后续所有正式文档建议在开头显式包含以下元信息：

1. `文档状态`
2. `文档角色`
3. `适用范围`
4. `最后更新`

当前允许的状态如下：

1. `Active`: 当前有效的规则、说明或正式指南
2. `Draft`: 正在收敛中的文档，内容可参考但未完全定稿
3. `Proposal`: 提案型文档，表达方向但不是现行规则
4. `Archive`: 历史文档，仅保留回溯价值

没有状态说明的旧文档，应默认视为待收口对象，而不是自动视为现行文档。

## 7. 文档目录角色建议

### 7.1 `docs/`

只放总入口文档、面向角色的总说明文档和一级索引。

### 7.2 `docs/development/`

放工程规则、开发规范、治理基线和执行方案。

### 7.3 `docs/api/`

放接口、契约、插件模型和核心能力参考说明。

### 7.4 `docs/architecture/`

放系统架构、运行链路、专题结构设计说明。

### 7.5 `docs/_archive/`

放确认退役的旧文档或已被新文档替代的历史方案。

## 8. 当前收口原则

文档收口应按以下原则执行：

1. 先修入口文档，再修专题文档。
2. 先明确权威关系，再决定是否重写全文。
3. 能通过状态说明和角色调整解决的，不急于大规模重写。
4. 文档若仍有参考价值，应先降级为 Draft / Proposal，而不是直接删除。
5. 只有当新文档已经形成明确替代关系时，才把旧文档转入 Archive。

## 9. 当前阶段建议收口顺序

### Phase 1: 入口收口

目标：让任何新读者都能找到正确入口。

范围：

1. `docs/README.md`
2. `docs/00-设计概要.md`
3. `docs/03-开发指南.md`
4. 根 `README.md` 中的文档入口

### Phase 2: 权威关系收口

目标：让旧文档不再和新文档并列争夺总解释权。

范围：

1. `docs/01-设计愿景.md`
2. `docs/architecture/01-System_Overview.md`
3. `docs/api/01-Nexus_Core_API.md`

### Phase 3: 专题文档收口

目标：按实际工程状态继续补齐 Active / Draft / Proposal 的边界。

范围：

1. `docs/development/01-04`
2. `docs/development/07-10`
3. 其他 API / architecture 文档

### Phase 4: 归档与目录整理

目标：将已确认退役的旧叙事转入 `_archive/` 或补 Archive 标记。

## 10. 文档更新触发规则

后续出现以下变更时，必须同步检查 docs：

1. 仓库目录结构变化
2. 构建入口变化
3. 版本事实源变化
4. 平台支持边界变化
5. API 或契约入口变化
6. CI / 发布流程变化

如果代码已变而文档未变，应默认视为工程缺口，而不是“文档以后再说”。

## 11. 当前执行结论

Nexus 的文档体系后续不应再按“想到什么写什么”的方式增长，而应围绕以下稳定结构收敛：

1. `00-设计概要` 负责整体定义。
2. `03-开发指南` 负责研发入口。
3. `11-Repository_Governance_Baseline` 负责仓库治理总纲。
4. `12-Documentation_Governance_and_Closure_Plan` 负责 docs 自身治理。
5. API 与架构文档退回到“参考层”角色，并通过状态说明逐步收口。

这套结构稳定之后，docs 才能真正成为 Nexus 的开发指引体系，而不是一组历史文档集合。
