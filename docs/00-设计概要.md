## 2. Nexus 的定义

Nexus 是一个面向网络分析、网络诊断、测试工具编排和现场问题排查的桌面平台。

它不是单一功能工具，而是一个统一宿主，用于将多类网络能力组织到同一套产品结构中，包括但不限于：

1. 网络连通性与时延分析
2. 吞吐性能测试
3. 协议或业务侧数据分析
4. 本地或远端抓包能力
5. 自动化操作与辅助流程
6. 面向后续扩展的插件化工具承载能力

从产品形态上看，Nexus 当前是一个以桌面 GUI 为主入口、以 Python 核心逻辑为主能力层、以 React 前端作为交互界面的网络分析平台。

## 3. 项目目标与核心价值

Nexus 的目标不是简单堆叠若干网络工具，而是提供一套可以持续演进的统一分析工作台。

其核心价值包括：

1. **统一承载**: 将原本分散的网络诊断、抓包、性能测试、分析与自动化能力收敛到一个可维护的平台中。
2. **前后端解耦**: 将工具逻辑与界面展现解耦，使系统既可作为桌面产品演进，也可保留逻辑层独立发展的空间。
3. **插件化扩展**: 通过契约层、核心层和宿主层分离，为后续工具扩展与能力增长提供长期结构基础。
4. **工程化交付**: 通过统一构建入口、版本事实源、产物目录和最小 CI，逐步从个人项目进入正式工程治理状态。
5. **跨平台演进**: 在不牺牲 Windows 主线可用性的前提下，逐步建立 macOS 和 Linux 的可验证支持能力。

## 4. 问题域与适用场景

Nexus 面向的问题域主要是网络问题排查和分析工作中的“工具碎片化”与“流程割裂”。

典型场景包括：

1. 快速执行 Ping / iPerf / 抓包等基础网络诊断动作
2. 在同一界面中查看实时数据、分析结果和工具输出
3. 将分析逻辑、管理逻辑和交互逻辑分层维护，避免工具越堆越乱
4. 将现场支持、研发调试和实验性分析能力放在同一个产品壳层中持续演进

当前阶段，Nexus 更偏向内部研发与技术型用户的专业工具平台，而不是面向泛大众用户的消费级软件。

## 5. 项目边界

### 5.1 当前纳入边界的内容

Nexus 当前明确纳入范围的内容包括：

1. 基于桌面宿主的网络分析与工具编排平台
2. 以 Python 为主的逻辑实现层和工具运行能力
3. 以 React + pywebview 为主的桌面前端交互层
4. 契约层、核心层、宿主层三层分离的 monorepo 工程结构
5. 构建、版本、文档、CI 和平台支持的工程治理体系

### 5.2 当前明确不纳入边界的内容

为避免项目定义持续膨胀，当前阶段不把以下内容定义为本轮必须完成的目标：

1. 通用云服务平台或在线 SaaS 产品
2. 全平台功能完全一致的发布承诺
3. 一次性覆盖所有网络分析场景的“大而全平台”
4. 面向第三方生态开放的成熟 SDK 体系
5. 当前阶段的正式商业化安装器、签名、公证和完整发布链路

### 6.1 当前产品版本

当前产品版本事实源位于 `nexus-platform/config/versions.json`，当前 `app` 版本为：

1. `1.7.0`

该版本用于代表当前对外产品语义，不等同于某个单独 Python 包或前端工程包的内部版本。

### 6.2 当前仓库阶段判断

当前仓库已具备清晰 monorepo 结构，但整体仍处于“半迁移态”。

这意味着：

1. 新结构已经建立
2. 旧文档与旧叙事仍有残留
3. 新构建入口已经存在
4. 正式工程治理正在补齐

因此，Nexus 当前既不是早期原型，也还未完全进入成熟企业级交付状态，而是处于“核心产品结构已成型、工程体系正在系统化收口”的阶段。

## 7. 技术路线与总体架构

Nexus 当前采用三层架构：

1. `nexus-contracts`: 契约层
2. `nexus-core`: 逻辑实现层
3. `nexus-platform`: 桌面宿主层

这一结构的目标，是把“能力定义”“能力实现”“产品承载”三种职责拆开，而不是继续把所有逻辑堆进单一应用目录。

### 7.1 契约层 (`nexus-contracts`)

职责：

1. 承载共享类型
2. 承载节点元数据装饰器
3. 承载通用异常
4. 为跨层协作提供稳定的公共接口基础

这一层应保持轻量、稳定、低依赖，并避免反向依赖核心层或宿主层。

### 7.2 逻辑层 (`nexus-core`)

职责：

1. 提供工具实现与分析能力
2. 承载协议处理、数据处理与业务逻辑
3. 通过插件目录组织具体工具能力
4. 尽量保持不依赖 GUI 环境

这一层是 Nexus 的“能力引擎”，重点是逻辑实现，而不是交互呈现。

### 7.3 宿主层 (`nexus-platform`)

职责：

1. 提供桌面 GUI 入口
2. 承载前后端桥接
3. 管理窗口、平台能力、工具调用与状态同步
4. 负责前端资源、宿主配置、打包与桌面交付

这一层是 Nexus 的“产品外壳”，负责把核心能力真正组织成可使用的桌面产品。

## 8. 系统构成

从运行时视角看，Nexus 的主要组成包括：

1. React 前端
2. pywebview 桌面壳层
3. Python 后端 API 与 managers
4. `nexus-core` 工具与分析逻辑
5. 构建系统、profiles 与外部工具资源

### 8.1 前端系统

前端位于 `nexus-platform/frontend/src/`，技术栈包括：

1. React
2. Vite
3. TailwindCSS
4. `recharts`
5. `lucide-react`

前端负责：

1. 提供导航、工具面板和可视化界面
2. 调用后端暴露的 `window.pywebview.api`
3. 通过 `window.dispatchEvent` 接收后端事件
4. 根据平台能力和功能 profile 控制界面显隐

### 8.2 宿主后端系统

宿主后端位于 `nexus-platform/backend/`，负责：

1. 桥接前后端调用
2. 初始化各 manager
3. 暴露桌面 API
4. 管理平台能力和运行环境差异
5. 协调工具执行、状态管理和结果回传

### 8.3 核心工具系统

核心工具实现位于 `nexus-core/nexus_core/`，尤其是 `plugins/` 目录下。

当前已包含或正在围绕以下方向构建能力：

1. Ping
2. Advanced Ping
3. iPerf
4. 无线抓包与相关能力
5. RTP / BA 等分析方向
6. 其他网络分析或自动化工具

### 8.4 平台能力系统

平台能力由 `nexus-platform/backend/capabilities.py` 暴露，用于显式声明当前平台可用功能，而不是默认假设所有平台都支持相同能力。

当前显式建模的能力包括：

1. `automation`
2. `customWindowChrome`
3. `adminElevation`
4. `wirelessCaptureLocalControl`
5. `wirelessCaptureRemoteControl`
6. `toolMultiWindow`

## 9. 平台策略与支持边界

Nexus 当前采用分级平台策略，而不是对所有平台做同等承诺。

### 9.1 Windows

Windows 是当前主成熟平台。

其定位是：

1. 当前最完整的能力承载平台
2. 自动化、本地系统集成和窗口增强能力的主战场
3. 正式发布路径的主要落点

### 9.2 macOS

macOS 当前目标不是一次性补齐所有能力，而是：

1. 稳定启动 GUI
2. 保证核心通用能力可用
3. 逐步纳入构建、验证和产物治理链路

### 9.3 Linux

Linux 当前仍处于较早阶段。

现阶段更合理的定位是：

1. 逐步建立最小可验证支持
2. 先保证构建与导入层面的基础可验证性
3. 后续再讨论更完整的产品支持范围

## 11. 目录与仓库组织

Nexus 当前采用 monorepo 组织，而不是把所有能力混在单项目结构中。

当前根目录的主要职责划分为：

1. `docs/`: 正式文档与规范中心
2. `build-system/`: 统一构建逻辑
3. `profiles/`: 功能档位与构建档位定义
4. `scripts/`: 仓库级包装脚本
5. `tools/`: 外部工具资源与 manifest
6. `artifacts/`: 构建产物输出目录
7. `nexus-contracts/`: 契约层包
8. `nexus-core/`: 逻辑实现层包
9. `nexus-platform/`: 桌面宿主层项目

这种结构的意义是：

1. 让目录名称与职责语义一致
2. 避免宿主层承担全部历史负担
3. 为版本、构建、产物和工具治理提供明确落点

## 12. 构建与交付设计

### 12.1 统一构建入口

Nexus 当前的真实构建入口是：

1. `build-system/build.py`

它负责：

1. 读取 build profile
2. 读取 feature profile
3. 解析构建计划
4. 运行只读校验
5. 执行前端构建
6. 执行 PyInstaller 打包
7. 产生产物与 manifest

### 12.2 Profile 体系

Nexus 的构建与交付不是继续依赖一组分散脚本，而是逐步转向 profile 驱动。

其中：

1. `profiles/builds/` 定义目标平台、打包格式、产物目录、签名策略和 bundled tools
2. `profiles/features/` 定义功能档位、外部依赖策略和 UI 可见性策略

这意味着，Nexus 的“发布变体”由平台、能力档位和交付形式共同决定，而不是只由脚本名决定。

### 12.3 当前产物形态

当前仓库已定义的典型产物方向包括：

1. Windows release: `exe / one-file`
2. Windows debug: `exe / one-file`
3. macOS demo: `app / one-folder`

产物输出统一进入 `artifacts/` 目录树，而不是继续散落在历史路径中。

### 12.4 外部工具治理

Nexus 对外部工具的处理采用 manifest 驱动，而不是在代码中硬编码猜测目录。

当前 `tools/manifests/tools.json` 已用于描述 bundled tool 资产，例如：

1. `iperf3`
2. `iperf2`

其长期意义是：

1. 区分系统命令、bundled 工具、外部依赖和远端依赖
2. 让构建系统按目标平台解析需要打入产物的工具资产

## 13. 版本设计

当前版本体系已明确区分“产品版本”和“包版本”。

### 13.1 产品版本

产品版本以 `nexus-platform/config/versions.json` 中的 `app` 为事实源。

### 13.2 包版本

包版本分别由各子项目维护：

1. `nexus-core` 在自身打包元数据中维护
2. `nexus-contracts` 在自身打包元数据中维护

### 13.3 当前版本治理原则

1. 不再新增第四套平行产品版本源
2. 文档中必须明确说的是产品版本还是包版本
3. 构建系统与产物 manifest 应围绕产品版本持续收敛

## 14. 质量门禁与 CI

Nexus 已开始建立最小 CI 门禁，而不再完全依赖人工经验。

当前最小验证 workflow 覆盖：

1. Python 依赖安装
2. 前端依赖安装
3. 前端构建
4. Python 源码编译检查
5. 只读 build-plan 校验

这一层不是最终形态，但它已经把“是否还能基本构建与解释当前仓库”从口头判断转为机器可验证。

## 15. 当前规划与演进方向

Nexus 的演进不是“无限扩功能”，而是围绕三个方向并行推进。

### 15.1 产品能力演进

继续完善网络分析、性能测试、抓包和自动化等能力，但前提是结构边界清晰，不再靠持续堆叠页面和脚本扩张。

### 15.2 工程治理演进

继续收敛：

1. 目录结构
2. 版本事实源
3. 构建入口
4. 文档状态
5. CI / CD

### 15.3 平台支持演进

继续保持：

1. Windows 作为主成熟平台
2. macOS 先保证启动稳定与核心能力可用
3. Linux 先建立最小可验证支持

## 16. 当前风险与约束

当前需要明确承认的风险与约束包括：

1. 仓库仍处于半迁移态，历史文档和历史叙事尚未完全清理
2. 部分平台能力尚未完成真正的全链路验证
3. 第三方工具的多平台资产治理仍未完全补齐
4. 正式签名、公证和完整发布链路仍在后续范围内
5. 部分旧开发文档仍带有过时路径和过时结构描述

这些问题不改变 Nexus 作为项目立项的合理性，但意味着项目需要继续以“结构收敛 + 能力演进”双线推进，而不是只看功能面。

## 17. 立项结论

Nexus 已经具备作为正式项目立项的基本条件：

1. **有明确的问题域**: 网络分析、网络诊断与工具统一承载
2. **有明确的产品边界**: 桌面平台，而非泛化平台或云服务
3. **有明确的系统结构**: 契约层、逻辑层、宿主层三层分离
4. **有明确的技术路线**: React + pywebview + Python + profile-driven build system
5. **有明确的工程化方向**: 版本、构建、CI、文档和平台治理已进入持续收敛阶段

因此，Nexus 当前最适合被定义为：

**一个面向专业网络分析与诊断场景、以桌面 GUI 为主入口、以 Python 核心逻辑为能力基础、正在从个人工程向正式项目治理收敛的统一平台。**
